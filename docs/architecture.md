# Software architecture

Samsung TV Remote is a local macOS application written in Rust. Its regular window uses [Iced](https://docs.rs/iced/0.14.0/iced/) and follows MVVM. The application uses Clean Architecture: product policy lives in the center; UI, network protocols, and macOS services are adapters. User input becomes a typed application command before it can affect a TV.

This document defines the intended design. The current crate includes the Iced
shell, application coordinator, and secure P1-M10 live adapters. P1-M11 moved
live workflow policy from Iced into the application layer and renamed the
semantic center action to `Enter`. The [repository architecture](planned-repository-architecture.md)
maps the implemented modules; later features remain planned below.

The first usable app covers local-network TV discovery, manual host entry, navigation, volume, mute, power control, wake, source selection, installed TV app launch, and text input. Power-off, wake, source, app, and text controls remain conditional on observed support by the selected TV; an unsupported operation produces an explicit explanation. The main app window opens to the Remote View, restores the most recently selected saved TV, and attempts its Connection using the normal reconnect policy. Its Main Toolbar opens a separate Settings Window, where TV selection and discovery live. Iced is the selected macOS window toolkit.

## Layers and dependency rule

```text
Iced view + ViewModel     macOS, WebSocket, discovery, storage adapters
          \                         /
           \                       /
             application use cases
                      |
                    domain
```

Source dependencies point inward. `domain` knows only product concepts. `application` uses domain types and defines ports for external capabilities. `presentation` and `infrastructure` depend on those inner contracts; neither is imported by the inner layers. The composition root in `main.rs` creates concrete adapters and wires them to the application. Keep the project as one Cargo package until a real build or ownership need justifies separate crates.

| Layer | Owns | Must not own |
| --- | --- | --- |
| Domain | Stable local device identity, supported actions, device capabilities, and action rules | Iced types, live connection state, JSON, sockets, Keychain APIs |
| Application | Use cases for discovering, pairing, connecting, sending actions, waking, and forgetting a TV; connection/pairing state, typed outcomes, ports, cancellation and retry policy | Widgets, Samsung wire frames, OS storage calls |
| Presentation | Iced views, ViewModels, keyboard and pointer mapping, feedback and accessibility text | Raw TV keys, tokens, socket ownership |
| Infrastructure | Samsung protocol codec and session, discovery, Wake-on-LAN, preferences, macOS Keychain and network-access error mapping | Product decisions or UI state |

The domain's `RemoteAction` is a finite set of button intentions such as `Up`, `Enter`, `VolumeDown`, and `PowerToggle`. An application `Command` adds context through requests such as `SelectDevice(device)`, `Connect(device)`, `Send(device, action)`, `SetVolumeLevel(device, level)`, `Wake(device)`, `SelectSource(device, source)`, `LaunchApp(device, app)`, `SendText(device, text)`, or `Forget(device)`. A Samsung adapter maps an allowed button action to a model-aware `KEY_*` value and protocol frame. Expose a distinct `PowerOff` action only if the selected TV has a verified off-only action; a toggle key remains `PowerToggle` even when the TV appears on. Exact volume setting is a separate typed operation, admitted only for a verified range and a TV with both exact-level write support and a fresh numeric volume observation; a step key cannot implement a slider value. Source selection, app launch, and text entry have their own typed operations because they have different preconditions and outcomes. No view supplies an arbitrary key string, app ID, or JSON frame. A generated local `DeviceId` identifies the saved record, not the TV itself. An advertised name, IP address, or MAC address alone cannot rebind that record to another host. A host change must pass the saved trust check before a token is sent, or require explicit renewed trust.

## MVVM and command-based input

An Iced view reads the ViewModel's current projection and emits a presentation `Message`. The application is authoritative for the Selected TV, Pairing, Connection, capability, and text-session state. The ViewModel projects those facts, pending indicators, and user-facing error text. Choosing a Saved TV row emits `SelectDevice`; the Remote View changes its Selected TV label and control target only after the application reports the new generation. A checked Discovered TV row is a provisional choice during confirmation and Pairing, not yet the Selected TV. The ViewModel's transition handles a message and returns zero or more application commands; it does not execute I/O or construct Iced effects. The Iced adapter submits commands to the application in message order, then maps outcomes back to messages. Fast control commands enter the application's nonblocking, bounded dispatcher immediately; one-off Iced `Task<Message>` values await longer operations such as discovery and connection. `Subscription<Message>` delivers keyboard input and continuing session events. These are Iced runtime mechanisms; the application `Command` is a product-level request with no Iced dependency. [Iced's application, task, and subscription model](https://docs.rs/iced/0.14.0/iced/).

```text
button / keyboard shortcut
  -> Iced Message -> ViewModel transition -> application Command
  -> ordered dispatcher -> use case -> port -> adapter -> TV or macOS service
  -> typed result / session event -> Iced Message -> ViewModel -> view
```

The input mapper gives a button and its keyboard shortcut the same command. It suppresses remote shortcuts while a text field or modal owns the key, ignores unintended auto-repeat for non-repeatable actions, and never lets a window shortcut bypass pairing, capability, or connection checks. The Iced view stays free of network and storage calls. [Iced keyboard subscriptions](https://docs.rs/iced/0.14.0/iced/keyboard/index.html) can deliver input to this mapper.

Every device-specific request includes its `DeviceId`; discovery and manual-add requests do not yet have one. The application checks operation-specific preconditions: selected device, pairing and trust when required, a live connection when required, and known capability where available. An unknown capability remains distinct from an observed unsupported capability and requires a conditional user action where probing is appropriate. Switching devices or forgetting one cancels queued and pending work and clears its text-entry state. Cancellation cannot retract bytes already written to a socket, so an in-flight action can have an uncertain outcome. Physical TV actions are not undoable; the command model records intent and outcome, not an undo stack.

## Device sessions and effects

The application owns one active-device coordinator and one bounded outbound command queue. Its dispatcher validates a request, assigns a `RequestId` and selection generation, and either admits it in Iced message order or returns a typed rejection (`busy`, `not connected`, `pairing required`, `unsupported`, or another specific precondition). There is no second adapter queue. The infrastructure session owns the socket and performs one write at a time for commands delivered by the coordinator; it reports typed transport results and incoming TV observations, without choosing retries or user-facing status. Independently scheduled Iced tasks must not race to enqueue button presses. A full queue returns busy without growing or silently dropping commands. Subscribing to state must not open another connection. UI updates remain responsive while probing, pairing, sending, or reconnecting. [Iced subscription lifecycle](https://docs.rs/iced/0.14.0/iced/struct.Subscription.html).

Every admitted request has exactly one terminal result: `cancelled_before_write`, `not_sent`, `written`, or `uncertain`. `Accepted` is admission, not completion. `NotSent` requires evidence that no bytes were handed to the transport; an ambiguous or partial write is `uncertain`. A separately correlated TV observation may promote a written request to `confirmed`, but confirmation is never inferred from a socket write, a later connection loss, or a generic state change. Most remote keys have no reliable confirmation event, so the UI normally reports that a command was sent, not that the TV changed state. Do not replay uncertain actions automatically, especially power, mute, navigation, source, app launch, and text. Reconnect with bounded backoff for later user commands; stop on cancellation, token rejection, or certificate change. Switching TVs or forgetting one cancels queued commands before write, invalidates its generation, and closes its session. A write already in progress may finish or be uncertain; its result remains attached to the old TV and cannot update the new TV's status.

### Control and monitoring contract

The application exposes a `ControlSnapshot` and sequenced `ControlEvent`s through a read-only observation port. The snapshot contains an optional selected `DeviceId` and its generation, pairing state, connection state and last transition time, per-operation capability evidence (`unknown`, `supported`, or `unsupported`), wake and text-session state, pending `RequestId`s, and recent terminal results. It does not claim a current power, input, mute, or numeric volume value unless the TV actually reports that value with a known freshness and source. A stale observation becomes unknown after its connection or validity period ends. Keep command intent, transport outcome, and observed TV state as separate fields; a sent `VolumeUp` request cannot move a numeric volume indicator by itself.

The coordinator serializes state changes and assigns a monotonically increasing event revision. Observer attachment returns an atomic snapshot and its revision, then only later events. A subscriber detects a gap, restart, or selection-generation change and requests a fresh snapshot before applying further events. Replaceable status updates may be coalesced; terminal request results remain in a bounded, in-memory result journal until the UI acknowledges them. If that journal reaches capacity, admission applies backpressure and returns `busy` rather than evicting an unobserved result. Closing the app can discard this nonpersistent journal; on the next launch, do not imply a prior action succeeded. A request's status indicator is cleared only after its terminal result is rendered or acknowledged, so a restarted subscription cannot leave a permanent spinner. Diagnostics use the same typed categories without storing private device data.

The ViewModel derives a small, accessible status projection from the snapshot: selected TV identity; Pairing and Connection separately; the current operation's admission, pending, sent, confirmed, uncertain, or failed state; and a relevant recovery action. It never treats a quiet event stream as proof that the TV is healthy. Connection liveness comes from the session's explicit connect, close, timeout, and heartbeat or probe observations. Show pairing pending, declined, re-pair required, unreachable, local-network access denied, and wake timeout as distinct states. Do not run a probe on every button press; keep monitoring bounded and cancellable, and avoid background reconnect loops when the user has switched TVs or denied access.

The application also exposes a bounded, session-only activity projection of recent request outcomes and Connection events for a separate Activity View. It records event time, operation, outcome, and a safe device display label or local record reference; it does not store wire payloads, text drafts, tokens, addresses, or untrusted app parameters. The presentation shell maps typed application events and user-relevant Settings Window events into one app-wide message feed for the Global Messages Pane. This feed is presentation state: adapters cannot publish user-facing strings, and the application cannot depend on window or widget types. Give each message a monotonic sequence, timestamp, severity, source, and optional request reference. Both windows publish to the same feed; duplicate event delivery after resubscription must not create duplicate messages. Preserve message order even when asynchronous operations complete out of order by ordering at publication time and retaining the referenced request ID. Keep the feed bounded in memory for the current app session, with a clear oldest-message eviction rule and no secret-bearing content. A newly opened main window reads the current feed snapshot before live additions. Immediate status near a control and a global message may refer to the same event but must use the same underlying outcome.

The primary awake-TV adapter uses the community-observed local Tizen WebSocket remote channel over `wss` on port 8002. The owner has ruled out plaintext port 8001 for P1-M10. The adapter owns endpoint probing, pairing token exchange, frame parsing, key mapping, transport timeouts, and model-specific capability probes. It reports evidence through the port; the application decides whether an action is available and when evidence becomes stale. Keep this protocol behind an application port because Samsung does not publish it as a stable third-party consumer remote API. [Local protocol research](research/samsung-tv-remote-protocol.md), [interoperable command reference](https://github.com/xchwarze/samsung-tv-ws-api/blob/master/COMMANDS.md).

### Sources, TV apps, and text

Source selection maps a typed, known source to a model-specific direct key when validated. Otherwise, offer the TV's source chooser and let the user navigate it; do not automate an unknown menu path. A socket write means the source change was requested, not observed. Installed TV apps come from that TV's channel events, with app IDs cached per device and refreshed when stale or after a clear launch failure. Treat catalog data as untrusted and bound its size and field lengths. Launch only an app selected from the active device's catalog; check that membership again at dispatch. Report “launch requested” until the TV provides stronger evidence. [Source and app research](research/source-changes-and-app-launches.md).

Text entry is a connection-scoped operation for a focused native Tizen input field. The session adapter parses IME start/end events and reports typed observations; the application owns `TextInputState`, and the ViewModel enables Send when that state allows it. If the target model does not emit IME events, a user-initiated send can remain available with a clear explanation that the TV field must already be focused. Bound text length and send the complete UTF-8 string through the Samsung text command, then end input on submission, cancellation, or focus loss when the connection permits. A normal Enter action remains separate and must not submit a TV form automatically. Clear the Mac-side draft after a known write or when the text session ends. If sending is uncertain, retain the draft in memory with a warning so the user can decide whether to retry; never retry it automatically. Mask sensitive entry when selected, and never persist or log text or encoded payloads. Direct text entry is conditional and does not imply support for streaming apps' custom on-screen keyboards. [Text-input research](research/samsung-tv-text-input.md).

Wake is a separate command through a Wake-on-LAN adapter, followed by bounded readiness checks and reconnect. It requires a previously saved device MAC address and appropriate TV/network settings; it does not imply that the TV is awake merely because a packet was sent. Cancel pending wake retries when the user cancels, selects another TV, or quits. The TV settings page runs a bounded, cancellable local-network discovery operation and lists saved TVs and deduplicated discovered candidates in a radio-button TV Selection Table above Discover TVs. Hide the table when it has no rows; auto-select its only row and require a user choice when multiple TVs are listed and none is active. Selecting a discovered candidate requires TV Identity Confirmation and pairing before saving it and making it active. At startup, always show the main app window in the Remote View; restore the most recently selected saved TV and attempt its Connection when one exists. With no Selected TV, leave the standard controls visible but disabled and show a short status line pointing to Settings. Do not add a first-run onboarding or automatically open Settings. Discovery is not proof of identity. Select the discovery mechanism after checking what the target TV advertises. Manual host entry remains available when discovery finds nothing or is unavailable. Constrain targets to the intended local network and require pairing/trust confirmation before saving one. [Wake research](research/samsung-tv-wake-on-lan.md), [Samsung Smart View wake capability](https://developer.samsung.com/smarttv/design/smart-view-sdk.html).

## Trust, storage, and macOS boundary

Store pairing tokens in macOS Keychain behind a `CredentialStore` port, scoped to the trusted device. Store ordinary preferences separately: user label, host, supported capabilities, and an approved wake MAC when needed. Keep certificate trust data device-scoped behind a `CertificateTrustStore` port. On first trust of a self-signed TV certificate, show the observed identity and fingerprint for user confirmation before sending a token or pairing request; also direct the user to confirm the approval prompt on the intended TV. A fingerprint read over an untrusted connection alone does not authenticate the TV. The TLS verifier checks the saved certificate pin before the WebSocket upgrade transmits a token-bearing request. Fail closed on a changed certificate and require renewed trust; do not carry an old token onto a newly trusted identity without re-pairing. P1-M10 has no port-8001 or TLS-to-plaintext fallback. Pairing is complete only after the token is saved successfully. A failed Keychain write leaves it visibly incomplete and must not persist a paired state. Forgetting a device attempts to remove its token and trust record and reports partial cleanup instead of claiming all credentials were removed. [Security research](research/samsung-tv-protocol-security.md), [Apple Keychain Services](https://developer.apple.com/documentation/security/keychain-services).

The macOS adapter owns Keychain access and packaging-related platform integration. The application bundle must explain local-network access with `NSLocalNetworkUsageDescription`. Explain access in the add/connect flow; the system presents its permission alert when the app first performs a local-network operation. If that operation fails while the alert is pending, show a recoverable state and offer retry after the user grants access. Bonjour declarations and network entitlements depend on the chosen discovery design. The initial installation audience is the owner of the target Mac; P1-M10 uses a locally self-signed, unnotarized bundle because the owner has no Apple-issued signing identity. A self-signed certificate does not provide a Developer ID identity recognized by Gatekeeper, and Apple says an Apple-issued signing identity is needed for reliable local-network privacy identity tracking. Validate permission behavior across rebuilt bundles on the target Mac and record any limitation. [Apple local-network privacy guidance](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy), [Apple Developer ID guidance](https://developer.apple.com/developer-id/).

Never log tokens, full WebSocket URLs, raw pairing frames, device addresses, MAC addresses, user-entered text, or app launch parameters. Diagnostics report a sanitized error category and operation, with correlation IDs that do not encode device data. Local device data remains local by default.

## Validation seams and unresolved compatibility

The application ports permit deterministic fakes for device sessions, discovery, wake, preferences, and secrets. Test the command policy, pairing transitions, cancellation, ordering, token rejection, uncertain-send handling, stale results, IME state, per-device app catalogs, duplicate or spoofed discovery candidates, and discovery timeout or permission failure without a physical TV. Protocol fixtures should contain synthetic identities, tokens, and text. The first compatibility target is KU75UA8090FXKR; the owner has verified Pairing, saved-token reconnect, and ten on-screen keys from a signed bundle, while broader support remains unverified. Aim for under 150 ms from a Mac control press to a visible TV reaction for ordinary keys while the TV is awake and connected on the home network. This target has not been measured and must not be claimed; app launches, wake, and pairing have different latency profiles. Hardware checks are still needed for native permission recovery, discovery, failure/switching paths, direct sources, app launch, native text entry, and wake. Any plaintext compatibility policy remains a decision informed by those checks.
