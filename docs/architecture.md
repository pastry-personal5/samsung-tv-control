# Software architecture

Samsung TV Remote is a local macOS application written in Rust. Its regular window uses [Iced](https://docs.rs/iced/0.14.0/iced/) and follows MVVM. The application uses Clean Architecture: product policy lives in the center; UI, network protocols, and macOS services are adapters. User input becomes a typed application command before it can affect a TV.

This document defines the intended design. The current crate contains only a minimal `src/main.rs`; the modules and interfaces below are planned in [planned repository architecture](planned-repository-architecture.md).

The first usable app covers local-network TV discovery, manual host entry, navigation, volume, mute, power control, wake, source selection, installed TV app launch, and text input. Power-off, wake, source, app, and text controls remain conditional on observed support by the selected TV; an unsupported operation produces an explicit explanation. Iced is the selected macOS window toolkit.

## Layers and dependency rule

```text
Iced view + ViewModel     macOS, WebSocket, discovery, storage adapters
          \                         /
           \                       /
             application use cases
                      |
                    domain
```

Source dependencies point inward. `domain` knows only product concepts. `application` uses domain types and defines ports for external capabilities. `presentation` and `infrastructure` depend on those inner contracts; neither is imported by the inner layers. The composition root in `main.rs` creates concrete adapters and wires them to the application. Keep the project as one Cargo package until a real build or ownership need justifies separate crates.

| Layer | Owns | Must not own |
| --- | --- | --- |
| Domain | Stable local device identity, supported actions, device capabilities, and action rules | Iced types, live connection state, JSON, sockets, Keychain APIs |
| Application | Use cases for discovering, pairing, connecting, sending actions, waking, and forgetting a TV; connection/pairing state, typed outcomes, ports, cancellation and retry policy | Widgets, Samsung wire frames, OS storage calls |
| Presentation | Iced views, ViewModels, keyboard and pointer mapping, feedback and accessibility text | Raw TV keys, tokens, socket ownership |
| Infrastructure | Samsung protocol codec and session, discovery, Wake-on-LAN, preferences, macOS Keychain and network-access error mapping | Product decisions or UI state |

The domain's `RemoteAction` is a finite set of button intentions such as `Up`, `Select`, `VolumeDown`, and `PowerOff`. An application `Command` adds context through requests such as `Connect(device)`, `Send(device, action)`, `Wake(device)`, `SelectSource(device, source)`, `LaunchApp(device, app)`, `SendText(device, text)`, or `Forget(device)`. A Samsung adapter maps an allowed button action to a model-aware `KEY_*` value and protocol frame. Expose `PowerOff` only if the selected TV has a verified off action; if its available key toggles power, label and type that action `PowerToggle` instead. Source selection, app launch, and text entry have their own typed operations because they have different preconditions and outcomes. No view supplies an arbitrary key string, app ID, or JSON frame. A generated local `DeviceId` identifies the saved record, not the TV itself. An advertised name, IP address, or MAC address alone cannot rebind that record to another host. A host change must pass the saved trust check before a token is sent, or require explicit renewed trust.

## MVVM and command-based input

An Iced view reads the ViewModel's current projection and emits a presentation `Message`. The ViewModel owns visible device selection, a projection of application connection state, pending indicators, and user-facing error text. The application is authoritative for pairing, connection, and text-session state. The ViewModel's transition handles a message and returns zero or more application commands; it does not execute I/O or construct Iced effects. The Iced adapter submits commands to the application in message order, then maps outcomes back to messages. Fast control commands enter a nonblocking, bounded mailbox immediately; one-off Iced `Task<Message>` values await longer operations such as discovery and connection. `Subscription<Message>` delivers keyboard input and continuing session events. These are Iced runtime mechanisms; the application `Command` is a product-level request with no Iced dependency. [Iced's application, task, and subscription model](https://docs.rs/iced/0.14.0/iced/).

```text
button / keyboard shortcut
  -> Iced Message -> ViewModel transition -> application Command
  -> ordered dispatcher -> use case -> port -> adapter -> TV or macOS service
  -> typed result / session event -> Iced Message -> ViewModel -> view
```

The input mapper gives a button and its keyboard shortcut the same command. It suppresses remote shortcuts while a text field or modal owns the key, ignores unintended auto-repeat for non-repeatable actions, and never lets a window shortcut bypass pairing, capability, or connection checks. The Iced view stays free of network and storage calls. [Iced keyboard subscriptions](https://docs.rs/iced/0.14.0/iced/keyboard/index.html) can deliver input to this mapper.

Every device-specific request includes its `DeviceId`; discovery and manual-add requests do not yet have one. The application checks operation-specific preconditions: selected device, pairing and trust when required, a live connection when required, and known capability where available. An unknown capability remains distinct from an observed unsupported capability and requires a conditional user action where probing is appropriate. Switching devices or forgetting one cancels queued and pending work and clears its text-entry state. Cancellation cannot retract bytes already written to a socket, so an in-flight action can have an uncertain outcome. Physical TV actions are not undoable; the command model records intent and outcome, not an undo stack.

## Device sessions and effects

Use one long-lived session owner for the active TV. The application dispatcher accepts control commands in Iced message order and passes them through a bounded queue to the session owner. The owner serializes outbound frames, receives channel events, and reports state changes through an application event stream. Assign a request sequence when admitting each command; independently scheduled Iced tasks must not race to enqueue button presses. Admission returns accepted or busy, while completion reports written or uncertain. A full queue returns busy without growing or silently dropping commands. Only the session owner holds the socket. Subscribing to its event stream must not open another connection. Attach an observer with a consistent state snapshot and subsequent sequenced events; resync after missed events or a subscription restart. Keep the event stream bounded, coalescing replaceable state updates but never silently losing a command completion. UI updates remain responsive while probing, pairing, sending, or reconnecting. [Iced subscription lifecycle](https://docs.rs/iced/0.14.0/iced/struct.Subscription.html).

Distinguish `accepted`, `written`, `confirmed`, and `uncertain` outcomes. Most remote keys have no reliable confirmation event, so the UI normally reports that a command was sent, not that the TV changed state. A failed write may still have reached the TV: do not replay any uncertain action automatically. In particular, never retry a power action as if it were idempotent. Reconnect with bounded backoff for later user commands; stop on cancellation, token rejection, or certificate change. Reject late results from a previous device selection or connection attempt using an operation or session generation ID. Show pairing pending, declined, re-pair required, unreachable, local-network access denied, and wake timeout as distinct states.

The primary awake-TV adapter uses the community-observed local Tizen WebSocket remote channel. Prefer `wss` on port 8002. The adapter owns endpoint probing, pairing token exchange, frame parsing, key mapping, timeouts, and model-specific capability checks. Keep this protocol behind an application port because Samsung does not publish it as a stable third-party consumer remote API. [Local protocol research](research/samsung-tv-remote-protocol.md), [interoperable command reference](https://github.com/xchwarze/samsung-tv-ws-api/blob/master/COMMANDS.md).

### Sources, TV apps, and text

Source selection maps a typed, known source to a model-specific direct key when validated. Otherwise, offer the TV's source chooser and let the user navigate it; do not automate an unknown menu path. A socket write means the source change was requested, not observed. Installed TV apps come from that TV's channel events, with app IDs cached per device and refreshed when stale or after a clear launch failure. Treat catalog data as untrusted and bound its size and field lengths. Launch only an app selected from the active device's catalog; check that membership again at dispatch. Report “launch requested” until the TV provides stronger evidence. [Source and app research](research/source-changes-and-app-launches.md).

Text entry is a connection-scoped operation for a focused native Tizen input field. The session owner consumes IME start/end events and exposes a typed `TextInputState`; the ViewModel enables Send when the state allows it. If the target model does not emit IME events, a user-initiated send can remain available with a clear explanation that the TV field must already be focused. Bound text length and send the complete UTF-8 string through the Samsung text command, then end input on submission, cancellation, or focus loss when the connection permits. A normal Select action remains separate and must not submit a TV form automatically. Clear the Mac-side draft after a known write or when the text session ends. If sending is uncertain, retain the draft in memory with a warning so the user can decide whether to retry; never retry it automatically. Mask sensitive entry when selected, and never persist or log text or encoded payloads. Direct text entry is conditional and does not imply support for streaming apps' custom on-screen keyboards. [Text-input research](research/samsung-tv-text-input.md).

Wake is a separate command through a Wake-on-LAN adapter, followed by bounded readiness checks and reconnect. It requires a previously saved device MAC address and appropriate TV/network settings; it does not imply that the TV is awake merely because a packet was sent. Cancel pending wake retries when the user cancels, selects another TV, or quits. The add-device flow runs a bounded, cancellable local-network discovery operation and presents deduplicated candidates for user selection. Select the discovery mechanism after checking what the target TV advertises; never treat an advertisement as proof of identity. Manual host entry remains available when discovery finds nothing or is unavailable. Constrain targets to the intended local network and require pairing/trust confirmation before saving one. [Wake research](research/samsung-tv-wake-on-lan.md), [Samsung Smart View wake capability](https://developer.samsung.com/smarttv/design/smart-view-sdk.html).

## Trust, storage, and macOS boundary

Store pairing tokens in macOS Keychain behind a `SecretStore` port, scoped to the trusted device. Store ordinary preferences separately: user label, host, supported capabilities, and an approved wake MAC when needed. Keep certificate trust data device-scoped behind a `TrustStore` port. On first trust of a self-signed TV certificate, show the observed identity and fingerprint for user confirmation before sending a token or pairing request; also direct the user to confirm the approval prompt on the intended TV. A fingerprint read over an untrusted connection alone does not authenticate the TV. The TLS verifier checks the saved certificate pin before the WebSocket upgrade transmits a token-bearing request. Fail closed on a changed certificate and require renewed trust; do not carry an old token onto a newly trusted identity without re-pairing. Never silently fall back from TLS to plaintext. Whether port 8001 is offered at all depends on the TV test; if offered, it requires an explicit per-device choice. Pairing is complete only after the token is saved successfully. A failed Keychain write leaves it visibly incomplete and must not persist a paired state. Forgetting a device attempts to remove its token and trust record and reports partial cleanup instead of claiming all credentials were removed. [Security research](research/samsung-tv-protocol-security.md), [Apple Keychain Services](https://developer.apple.com/documentation/security/keychain-services).

The macOS adapter owns Keychain access and packaging-related platform integration. The application bundle must explain local-network access with `NSLocalNetworkUsageDescription`. Explain access in the add/connect flow; the system presents its permission alert when the app first performs a local-network operation. If that operation fails while the alert is pending, show a recoverable state and offer retry after the user grants access. Bonjour declarations and network entitlements depend on the chosen discovery design. The initial installation audience is the owner of the target Mac; a self-signed, unnotarized bundle is the local-build direction. A self-signed certificate does not provide a Developer ID identity recognized by Gatekeeper, and Apple says an Apple-issued signing identity is needed for reliable local-network privacy identity tracking. Validate permission behavior across rebuilt bundles on the target Mac. [Apple local-network privacy guidance](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy), [Apple Developer ID guidance](https://developer.apple.com/developer-id/).

Never log tokens, full WebSocket URLs, raw pairing frames, device addresses, MAC addresses, user-entered text, or app launch parameters. Diagnostics report a sanitized error category and operation, with correlation IDs that do not encode device data. Local device data remains local by default.

## Validation seams and unresolved compatibility

The application ports permit deterministic fakes for device sessions, discovery, wake, preferences, and secrets. Test the command policy, pairing transitions, cancellation, ordering, token rejection, uncertain-send handling, stale results, IME state, per-device app catalogs, duplicate or spoofed discovery candidates, and discovery timeout or permission failure without a physical TV. Protocol fixtures should contain synthetic identities, tokens, and text. The first compatibility target is KU75UA8090FXKR; this is a test target, not a verified support claim. Aim for under 150 ms from a Mac control press to a visible TV reaction for ordinary keys while the TV is awake and connected on the home network. Measure this on the target setup before claiming it; app launches, wake, and pairing have different latency profiles. Hardware checks are still needed before claiming the TV's endpoint, certificate behavior, keys, direct sources, app launch, native text entry, discovery mechanism, or wake path. Any plaintext compatibility policy remains a decision informed by those checks.
